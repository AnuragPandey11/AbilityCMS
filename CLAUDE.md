## Working on the backend

Python **3.12** specifically (`asyncpg==0.29.0` has no 3.13+ wheels).

**The local stack is Docker**, via [solarcms-backend/docker-compose.yml](solarcms-backend/docker-compose.yml): `solarcms-postgres` (timescale/timescaledb:2.17.2-pg16) on **5433**, `solarcms-redis` on 6379, `solarcms-emqx` on 1883/18083. `docker compose up -d` before anything else. ⚠ There is also a *native* Postgres 18 on **5432** (`/Library/PostgreSQL/18`) holding unrelated databases and an **empty** `solarcms` — connecting there yields "relation does not exist" on every table, which reads as a wiped database rather than the wrong port. `.env` (5433) is the correct one; `.env.local` and `.env.clientbroker` still say 5432 and are stale. If Docker Desktop is not running, Postgres, Redis and the dev broker are all down at once, and the symptom is the whole UI blank.

Five processes share only Postgres and Redis:

```
uvicorn solarcms.api.main:app            # REST + WebSocket
python -m solarcms.workers.ingest        # MQTT → decode → Redis + COPY batch
python -m solarcms.workers.alarm         # consumes stream:readings
python -m solarcms.workers.health_sweeper  # 60s staleness/frozen-value sweep
python -m solarcms.workers.scheduler     # report crons, escalation timers
```

Migrations are Alembic only (`alembic upgrade head`), currently `0001`–`0027`. **Roles are created outside them** — run `scripts/bootstrap_roles.sql` as a superuser first, since a migration role normally has no CREATEROLE. Seed with `python -m solarcms.cli seed` (idempotent).

Tests: `pytest tests/unit` is pure-`domain/` and needs nothing running; `pytest tests/integration` needs the migrated database. Lint and types must both stay clean: `ruff check .` and `mypy src/solarcms` (strict). `tools/simulate.py` publishes either topic shape and can induce faults (`--fault silent|frozen|underperform`) that are otherwise impossible to wait for.

## Architecture: the load-bearing decisions

**`domain/` is pure.** Plain Python values in and out, no DB, no network, no I/O — that is what makes the formulas (the part most likely to be wrong) testable and replaceable. Topic decoding, PR/CUF/availability, alarm debounce/hysteresis, health logic, tier selection, and SLD tree building all live there.

**Nothing is known yet about units, formulas, thresholds, or intervals.** Every placeholder lives in `domain/assumptions.py` and nowhere else, so the client's real table is a one-file edit. BACKEND_SPEC §12 lists them; a factor-of-1000 voltage error looks entirely plausible in the data, which is why this is enforced rather than advised. The exception, added 16 Sep 2026: the formulas in `DERIVED_TAG_FORMULAS` are **client-supplied**, transcribed from their sheet's FORMULA column, and are marked SUPPLIED rather than ASSUMED — except CUF, which they left blank.

**A calculated metric is a row, not a release.** `tags.formula` holds arithmetic over other Tag codes (`(HV_VOLTAGE_RY + HV_VOLTAGE_YB + HV_VOLTAGE_BR) / 3`) and `domain/derived.py` evaluates it — parsing with `ast` against a whitelist, so a formula typed by an administrator cannot call anything. Two scopes: `device` formulas read one Device's own Tags and run in ingest; `plant` formulas read dotted aggregates (`SUM.ENERGY_TODAY`, `AVG.GHI_CUMULATIVE`) and run in the scheduler, the only process that sees a whole Plant. Three rules worth holding: **a published value always beats a computed one**, so a meter that really transmits AVG VOLTAGE keeps its own; **a missing input yields undefined, never 0.0**, because a PR of zero and an unknown PR mean opposite things; and a Device derives a Tag **only when it is bound to all of that formula's inputs**, which is why nothing is configured per Device.

**Repeating signal groups are sliced per unit.** The Inverter schedules PV1–PV28; how many a given machine has is `devices.string_count`, not a property of the Model, because one datasheet covers a 12-string and a 24-string machine. `device_model_tags.repeat_index` marks the group and binding takes the first *n*. With no count recorded, **none** of the group is bound — twenty-eight Tags that never report look exactly like a broken Device.

**The dashboard is one fixed screen, and the sources are configuration.** Plants are wired differently — two MCR sections fed by an ICR on one, a rooftop array whose entire AC side is a net meter on another — so a **slot** is a *position* on the screen (`kpi.current_power`), not a Tag. Each slot carries an ordered list of candidates naming a Device **Type**, a Tag and an aggregation, and the first the Plant is actually bound for wins (`domain/slots.py`, catalogue in `domain/dashboard_spec.py`, tables in migration 0021). Three rules matter: resolution is *planned* against bindings and only then read against values, which is what separates "no settlement meter here" from "the meter has gone quiet"; provenance travels with every value, because 6.32 MW measured and 6.32 MW summed from twelve Inverters are different claims; and a missing source yields undefined, never 0.0. Per-Plant deviation is a row in `plant_dashboard_slot_overrides` with a `note` — **expected to be empty**, and that it is usually empty is what keeps it on the right side of Guardrail 2. A drag-and-drop canvas was rejected (MASTER §3.7): it makes each Plant a bespoke artefact nobody can compare with another.

**The SLD has two projections.** `domain/sld.py` builds the true `parent_device_id` tree — one box per Device, the view for finding *which* Inverter. `domain/sld_stages.py` folds every power-path Device Type into exactly four stages via `device_types.sld_stage` — **PV Array → Inverters → Transformer → Grid**, always those four in that order — which is the view for judging a Plant at a glance and comparing it with the next one. A stage with no Devices still renders, marked not instrumented: on a rooftop Plant that is normal, on an 8 MW Plant it is a Device nobody registered.

**The two projections take different *kinds* of input, and where they disagree a human decides.** `sld_stage` says which box a Device belongs in — per Type, global to every Client. `parent_device_id` says what feeds what — per Plant, and it says nothing about box membership, because a chain `A→B→C` gives relative position only. They part company on unusual topologies: an LT feeder meter wired between the Inverters and the Transformer is Type `MFM`, folds into **Grid**, and the schematic puts it third from the left — one meter, two positions, two screens. `domain/sld_conflicts.py` detects it by testing each wired edge (`position(upstream) <= position(downstream)`), anchored on the **upstream** Device so one disagreement is reported once rather than at both ends, and offers the stages that satisfy every wired neighbour. ⚠ It **reports, never resolves**: wiring is the more specific claim and should win, but it is hand-entered and verified against nothing — unlike a topic, which the broker states — so the disagreement is also the only cross-check there is, and silently letting one overrule the other would propagate a single mistyped parent into both diagrams. Accepting lands in `devices.sld_stage_override` (0027, nullable, expected empty), which is re-validated afterwards so an override the wiring has since made unnecessary is reported stale instead of rotting into a second source of truth. Detection runs on **edges only**, so an unwired Plant yields no conflicts rather than a page of them, and a half-wired one judges only the wired part. The suggested stage is the one **nearest the Type's own default**, not the leftmost allowed — with nothing wired into it a Device has no lower bound, and "leftmost" proposes PV Array for a meter.

**A Collector's edge is its occupants' connection, and every reader of the wiring must honour it.** A Device inside an enclosure has no `parent_device_id` of its own — the server *refuses* that edge, because seventeen Inverters in an MCR do not each run a cable to the transformer and the room owns the one that exists (0024). So anything deriving position from wiring must read `devices.parent_device_id` **or**, where that is NULL, `plant_collectors.parent_device_id` for the Device's `collector_code`. `SldTree` already did this — it hangs the whole box under the Device the room feeds — but the schematic and the commissioning root-count did not, so a correctly wired Plant read as entirely unwired and was told to make the one edit the server rejects. ⚠ This never makes a Collector a node: it is still drawn as a box *around* its occupants (Guardrail 12/14), and the edge only tells the row where those occupants sit. Hierarchy *within* an enclosure still wins, being the more specific claim. The UI for it is a "feeds into" selector per enclosure in Wiring & Diagram — a list, not a change to how the box is drawn.

**The schematic breaks ties by electrical position, and says so when it cannot derive one.** `buildStages` orders by generation-source, then depth, then `sld_stage` index. It used to fall through to the **type code, alphabetically** — which on an unwired Plant decides the entire row, because every Device ties at depth 0. On KULAR_GREEN that drew `INVERTER → MFM → TRANSFORMER → VCB`: the settlement meter upstream of the transformer, confidently, because `MFM` sorts before `TRANSFORMER`. ⚠ `parent_device_id` is set in **exactly one place** — the "feeds into" control in Wiring & Diagram — and is deliberately never inferred from the topic, never asked at registration and never derived from the payload, so a Plant nobody has wired has *no* electrical input at all. The view now states "hierarchy not set" rather than drawing a guess: a diagram that looks authoritative while being a default is worse than one that admits it.

**Every Plant has a `PLANT_KPI` Device** carrying its own figures (PR, CUF, peak power and its time, start/stop times, functional-Inverter count). This is the client's `DASHBOARD` row, renamed because "dashboard" already names a UI concept here. Its Tags are computed by `services/plant_kpi.py` every scheduler tick and copied to the YESTERDAY family at **23:55 Plant-local** — not UTC, or an Asia/Kolkata Plant attributes five and a half hours to the wrong day.

**Equipment is drawn, and the drawing never carries the status.** Every Device Type has a full-colour illustration (`components/devices/art/`, registry in `DeviceArt.tsx`) painted in the materials the equipment is made of — a transformer tank is grey, a module is deep blue — because in a diagram or on a card *the picture is the label*, and a monochrome silhouette of a transformer is the same shape as a monochrome silhouette of a switchgear cubicle at 40px. The status lives on the **frame around it**: the caller knows whether the Device is reporting, the drawing does not, and a transformer that turns green stops looking like a transformer. Two theme variables are the exception — `--art-rim` and `--art-shadow` are the drawing's relationship to the page behind it, not a material, so they invert with the theme while the tank stays grey. ⚠ `DeviceIcon` is **not** superseded: it renders a single-colour glyph through a CSS mask tinted with `currentColor`, which is right for a list row or a chip whose container is already coloured by state, and wrong wherever the picture is the only label. Both are keyed on `device_types.code`, so neither can drift from the catalogue without the other noticing.

**The dashboard fits one screen, and depth costs a click rather than a scroll.** `single_plant` was 6,110px — six and a half screens — with everything on it correct and nothing on it reachable, because seeing the second thing meant losing sight of the first. It is now ~1,150px: a headline strip, the four-stage schematic, two charts, an Inverter **carousel** (seventeen peers go sideways, not down), and a row of summary cards that each open their full detail in a **drawer** (`components/ui/Drawer.tsx`). A drawer rather than an in-place expander, because an expander satisfies the first click and destroys the property — the section below it moves and the page becomes a scrolling document again. Nothing was deleted; the *second* copy of each figure moved behind one click. Where the catalogue genuinely answers the same thing twice (`kpi.energy_today` and `energy.generated_today` both resolve to `sum` of `ENERGY_TODAY` over the same seventeen Inverters), `dashboards/single-plant/duplication.ts` drops the repeat — matching on **resolved source**, never on label or slot code, since the codes and labels differ and only the resolution makes them one fact.

**One Device, one inspector, everywhere it is clicked.** `components/devices/DeviceInspector.tsx` is the single answer to *what is this thing and why is it behaving like that* — identity and model, the three groupings, the topic, health and completeness, **every Tag the Device is bound to with its live value**, the payload key each is mapped from, and a 24-hour chart of any one of them. It replaced two smaller summaries that answered the same question differently depending on which screen found the Device; the diagram, the carousel, the health table, the SLD and the hierarchy editor now all open the same panel. Values are fetched for **every binding**, not just the caller's columns: rendering the full list against a card's handful made an Inverter read "6 of 18 reporting" and showed twelve dashes about the *query* rather than about the equipment. The unmapped-key section renders **only when there are any** — a section that says "nothing is wrong" on every Device is one people stop reading, exactly when it would matter.

**Overview and List were one screen wearing two names.** The tender names `plant_overview` and `plant_list` separately and never says how they differ, so this platform proposed cards-by-urgency versus a sortable table. Both drew the *same Plants from the same hook* and differed only in shape, and in the menu they read as two destinations for one job — the question in front of them was "which of these is the real one", which is a question a menu should never provoke. They are now one screen (`PlantsDashboard`) with a **view toggle**; nothing was dropped. Both codes still route, so a granted code and a pasted URL resolve (A-3), and `MERGED_INTO` in `navigation.ts` collapses them to one entry — ⚠ falling back to whichever code the User actually holds, so a Client granted only `plant_list` still gets in.

**A drawer that hands over to another drawer must not restore the page's scroll.** Each drawer used to snapshot `document.body.style.overflow` on open and write it back on close. The moment a stage list opens a Device, the second drawer mounts while the first still holds the lock, captures `"hidden"` as the value to restore, and puts it back when it closes — leaving the page **locked with no drawer on screen, unscrollable for the rest of the session**. `Drawer.tsx` counts instead: the first to open locks, the last to close restores, and a handover never touches the lock.

**A fleet figure is computed here, and a Plant that was never due to report gets no vote.** `dashboards/fleet/aggregate.ts` holds the arithmetic — Portfolio is computed, never stored (MASTER §1.1), so the rules live in the frontend and are tested there. The load-bearing one is `couldAnswer`: a Plant with **no Devices** answers `availability: 0.0` — a real number, not a null — so averaging it in reported **52.6% fleet availability** across one healthy Plant and two uncommissioned ones. Nothing was down; nothing was even connected. `coverage.expected_samples === 0` is the backend stating nothing was due, and that is the only thing distinguishing *not instrumented* from *instrumented and silent* — the second keeps its vote, because that zero is real and terrible. ⚠ Totals and means are deliberately asymmetric: an uncommissioned Plant's zero is arithmetically right in a **sum** of energy and nonsense in a **mean** of a ratio, which is why `fleetTotal` and `weightedRatio` are two functions.

**The navigation may not offer a dashboard whose screen refuses.** A Guest is granted `reports` by the database and the Reports screen requires `report.generate`, so the menu led straight to "this requires the report.generate permission". `DASHBOARD_REQUIRES` in `components/layout/navigation.ts` filters those out. ⚠ It grants nothing and enforces nothing — the screen and the server keep their own rules — and only a dashboard that cannot function *at all* belongs in it: hiding a whole screen because one button is unavailable takes away the reading a Guest is entitled to.

**Depth is the theme, not colour.** The screen was flat, and flat is not restraint: every surface sat at the same apparent height and nothing suggested a light source. Three things fix it and none of them adds a colour that *means* anything — a 1px inner highlight along the top of every raised surface (`--c-edge-top`, the whole trick: a card with a lit top edge reads as an object rather than a region), two very large very faint radial washes behind the app (`.app-ground`), and real layered shadows. The one hue in play is the brand accent on icon chips, used for "this is a headline metric" and nothing else. ⚠ Status owns green, amber and red on this platform, so a decorative tint near any of them would read as a judgement nobody made; that is why the washes are at 6–10% alpha and why `.lamp-ok` glows only on the healthy state.

**A chart under a tile must be the same claim as the tile.** `api/useSlotTrend.ts` does not name a Device Type or a Tag: it reads the slot the server already resolved, takes `source` off it, and asks `/readings` for exactly that — same Type, same Tag, same aggregate, same provenance string. Otherwise the screen shows a figure measured at the meter above a curve summed from the Inverters and invites somebody to read the difference as a loss. A Plant that cannot answer the slot gets no series rather than a fallback, because a fallback would be the frontend inventing a resolution rule. It aggregates **across Devices, never across time** — each bucket already carries the tier's own roll-up.

**Readings are narrow rows, never columns.** `(time, client_id, device_id, tag_id, value, quality, source_time)`. Device Models expose different Tag sets, so a wide table would be mostly NULL and every new model a migration. `client_id` is deliberately denormalised onto `readings` so row-level security and chunk pruning avoid a three-table join.

**Isolation is enforced by Postgres, not application code** — a forgotten `WHERE client_id` returns zero rows, not another Client's generation data. Four session variables (`app.user_id`, `app.client_id`, `app.role_code`, `app.is_platform_admin`) are set from verified JWT claims per transaction, alongside `SET LOCAL ROLE solarcms_api`, so the migration owner's privileges never serve a request. If a pooler is added, **PgBouncer must run in transaction mode**; statement mode leaks these between Clients and defeats the whole model.

**Telemetry isolation works differently, and the reason is not obvious.** TimescaleDB refuses RLS on a compressed hypertable (`columnstore cannot be used on table with row security`) in either order, which pits §5.3's compression sizing against §5.4's "RLS on every Client-owned table, including `readings`". Both are kept: `readings`, `mqtt_raw` and the `agg_*` tiers stay compressed with **no RLS**, and the API holds *no privilege at all* on them, reading only through `*_v` `security_barrier` views (migrations 0008 and 0010). **Never query `readings` from request-serving code** — it will fail, which is the design working. Plant scoping in those views rides on the RLS already enforced on `devices`, which is small by design (F-2).

**A Device has three independent groupings** and collapsing any two makes both unanswerable: `block_id` (where it is — geographic), `parent_device_id` (what it feeds into — electrical, the SLD), `reports_via_device_id` (what transmits it — communication). The third is what separates "communication loss" from "equipment downtime"; without it a failed collector is recorded as generation downtime and corrupts availability figures.

**A Collector is an enclosure, not a Device** (client-confirmed 19 Sep 2026; migration 0022). The `{collector_code}` segment of the topic names an MCR, an ICR, a panel — a box that *holds* equipment. It publishes nothing and carries no current, so it has no topic of its own and no place in the electrical tree, and commissioning no longer registers a Device for it. It lives in `devices.collector_code` as a **name**, beside `reports_via_device_id` rather than instead of it: "relayed by that datalogger" and "in the same room as that Inverter" are different claims, and the health sweep correlates on whichever is present (`CollectorKey = int | str`). Three consequences: the topic may also be five segments (`scms/v1/{client}/{plant}/{device}`) and `collector_code` NULL is then a real answer, not a gap; every diagram draws a Collector as a **dashed outline around** its Devices, and **an outline may never enclose a Device that is not in it** — `build_sld` keeps same-Collector siblings adjacent and `collectorBoxes` splits a group into several outlines rather than swallow a stranger; and `python -m solarcms.cli collectors-from-topics` (dry run by default) backfills the column from `source_address` and, with `--retire-devices`, deletes the Collector-Devices the old path created, re-pointing their children at *their* parent first so the chain closes over the gap.

**Onboarding reads the broker instead of asking.** The engineers publish before we onboard, so Client codes, Plant codes, Collectors, Device codes *and payload keys* are observable facts before any form is filled in. `api/routers/discovery.py` exposes them — `/discovery/clients`, `/discovery/plants`, `/discovery/topic` — so registering is confirming rather than typing, and a mistyped code can no longer produce a Device that looks registered and decodes nothing. ⚠ It reads **`mqtt_raw_v`, never MQTT**: Guardrail 3 forbids ingestion in the API process, and a second subscriber would compete for the same messages. The consequence is honest — this shows what ingest has *received*, so if ingest is down or the broker is unreachable, discovery is empty. ⚠ **Super Admin only**, not by choice: an unregistered topic is quarantined with `client_id = NULL` because attributing it by reading the topic is the inference Guardrail 5 forbids, so `mqtt_raw_v` shows those rows to a platform admin alone. Registration stays a separate, deliberate act — discovery only proposes. Two distinctions worth keeping straight: `registered_device_id` (is a Device registered for this topic *now*) is not `quarantined` (what happened to one message when it arrived), and reporting the second as the first tells an operator to fix something already fixed.

**"Feeds into" and "reports via" are never asked for at registration.** Both are *discovered*, not designed: which Collector transmits a Device is already stated by its topic, and what a Device is wired into is routinely corrected after the first day of real data. Asking at the moment of registration invites a guess, and a guess drawn into the Single Line Diagram is indistinguishable from a fact. Both remain first-class (MASTER §3.4) — they are simply set where they can be checked: the Collector by the topic, the wiring in Plant Hierarchy beside the diagram it produces. Removed from the onboarding wizard on 19 Sep 2026, along with the second PATCH pass that used to apply them.

**Adding a Device is topic-first, and discovery is the convenience on top — not the other way round.** `GET /plants/{id}/parse-topic` requires `plant.manage` (not `system.admin`) and returns only the structure of a string the caller typed, so it carries none of the isolation concerns that keep broker discovery Super-Admin-only. Paste the topic, and the Client, Plant, Collector and Device code are read back out of it against the live `topic_patterns` registry — never a second parser. ⚠ Getting this backwards was a real failure worth not repeating: registration was briefly possible *only* by picking from discovery, so the Client Admin who actually runs the Plant could add nothing at all, and equipment that had not started publishing yet could be registered by nobody. A related symptom: every Device read "not publishing" for those users, which asserted a fact there was no basis for — silence only means something when you could have heard.

**The Plant screen is organised by task, not by table.** `PlantEditor` (`/admin/plant-setup`) shows registered and not-yet-registered Devices in **one list**, matched on the topic — the only identifier both sides share, since a Device code alone would pair `MFM` inside the MCR with `MFM` outside it. A row expands into everything about that Device: topic, collector, measured interval, bound Tag count, the keys actually arriving with their mapping, and the raw payload. The previous split — Plant Setup owning `devices`, Plant Hierarchy owning `parent_device_id`, Device Bindings owning `device_tag_bindings` — was the schema showing through the interface; nobody thinks "I must edit device_tag_bindings", they think "what is wrong with INVERTER_7".

**A Client is never created without a login.** `POST /clients` takes an optional `first_user` and creates both **in one transaction** — a Client nobody can sign into looks finished on every screen and only its creator knows otherwise. The first User defaults to `admin` deliberately: `app_can_see_plant` grants an admin every Plant of their own Client, so Plants added later are visible with no extra grant, whereas any other role starts with zero Plants and Guardrail 7 means zero is none, never all.

**Planned Device counts are no longer asked for.** The onboarding input was removed on 19 Sep 2026: a count typed from a contract before any Device existed began drifting from reality the moment one was registered, and nothing depended on it enough to catch it being wrong. The Plant Setup screen shows the count that matters — `count(*)` over registered Devices, grouped by Type, derived and therefore incapable of drifting. The table and API field remain, unused, so no history is destroyed.

**The topic decides Collector membership; nothing else may.** Which room a Device publishes from is part of its origin, so Guardrail 5 governs it: a six-segment topic names the enclosure, a five-segment one states there is none, and in both cases a hand-typed `collector_code` is a contradiction rather than an override. `domain/decoding.collector_in_topic` returns `(known, code)` and the API refuses any create or update that disagrees — ⚠ `(True, None)` ("the topic says: no enclosure") and `(False, None)` ("no topic, so nothing is stated") are different answers and must never be collapsed, because only the second leaves room for a human to say. The one editable case is a Device registered before it has a topic; the Plant KPI panel is excluded even then, being synthetic and never destined to publish. The hierarchy editor renders the field as a read-only chip wherever the topic decides, and its "feeds into" list offers only Devices on the same side of the wall, so it never proposes an edit the server will refuse.

**A Collector owns one edge, and the boundary is a rule.** Migration 0024 gives the enclosure a row (`plant_collectors`: plant, code, `parent_device_id`, note) so the diagram can say *what the room feeds into* once, instead of repeating it on every occupant. ⚠ Still not a Device: no Model, no Type, no Tags, no topic, no Readings, and `devices` has no foreign key to it. **Membership stays `devices.collector_code`**, because that comes from the topic (Guardrail 5) — a Collector needs no row here to exist, so the table is sparse in the manner of `plant_dashboard_slot_overrides` and every join to it is LEFT. With the box owning an edge, a Device inside a Collector may not point at one outside it (`domain/sld.crosses_collector_boundary`, enforced in the API for the same reason cycles are: a CHECK cannot see the parent row, and a composite FK is satisfied vacuously when either side is NULL). Hierarchy *within* a Collector is unaffected and normal.

**The renderer draws Devices that carry no current; the electrical tree still does not contain them.** `build_sld` is unchanged and remains power-path only, because a Weather Station has no `parent_device_id` story and inventing one would corrupt the diagram (MASTER §2.3). What changed on 19 Sep 2026 is that `SldTree` now renders `excluded_not_in_power_path` as dashed, unwired nodes placed inside their Collector's box — so a WMS in the MCR looks like it is in the MCR — rather than hiding them in a side panel. The distinction is worth keeping straight: the *model* excludes them, the *picture* shows them.

**Absence is alarmed, and absence is what costs the owner money.** Every other rule compares a value that *arrived*; these fire on something that stopped, or never started. `domain/absence.py` decides which conditions should be open, `services/absence.py` writes the difference, and the **health sweep** evaluates them on its 60s timer — the alarm worker cannot, because it consumes the reading stream and absence produces no reading. Four rules, all `operator = 'special'`: `COMM_LOST` (one Device), `COLLECTOR_OFFLINE` (several sharing a Collector — **one** Alarm, never one per Device, because a failed datalogger recorded as seventeen equipment failures corrupts availability), `UNREGISTERED_DEVICE_PUBLISHING` (equipment publishing that nothing is registered for — its data is being discarded on every message), and `PLANT_SILENT` (a whole Plant delivering nothing, which no per-Device check can see because every per-Device check waits on data that is not coming). Everything is classified `communication`, never `equipment`: absence alone never proves which, and claiming downtime we cannot evidence understates availability against a performance guarantee. Debounce is **derived from the data each sweep** (the silence so far, how long a topic has published unregistered) rather than remembered between sweeps, so a restart cannot reset it. Migration 0025 adds `alarms.subject` — what a device-less Alarm is about — with its own partial unique index, because the original dedup index is on `(rule_id, device_id)` where NULLs are distinct and the same Collector would otherwise re-open and re-notify every minute.

**"Publishing now" and "published once" are different, and conflating them made the registration screen useless.** Discovery looks back 7 days and raw history is kept 90, so every topic shape a client migrates away from keeps offering itself as equipment to register for a week after it died. On KULAR_GREEN that read "+20 new" where all twenty were dead — a to-do list of corpses that buries the one row that matters. `domain/absence.classify_topic_liveness` judges a topic against **its own measured interval** (a fixed clock cannot: an 86s Device is late after three minutes, a daily total is fine after twenty hours), reusing the same multiplier the health sweep applies to a registered Device. Only `live` counts as a registration candidate. A retired topic can be dismissed (`discovery_ignored_topics`, `POST /discovery/ignored`) — reversible, audited, and it deletes nothing. `scripts/prune_topics.py` (dry run by default) removes dead raw history, and **never touches a registered Device's topic**: deleting its raw rows would destroy the evidence for the very outage that made it quiet.

**A late registration can get its history back.** Equipment that publishes before anyone registers it has every message quarantined — stored whole, decoded into nothing — so a machine running five days unregistered has five days no report will ever show. `services/backfill.py` replays them through the same `decode` the live path uses, stamped with each message's **own** receipt time (stamping them "now" would compress a week into one instant). It replays **only rows flagged `quarantined`** and clears the flag as it goes, which is what makes a re-run safe: `readings` has no unique constraint to lean on, because a uniqueness check on every inserted row is exactly what ingest cannot afford. ⚠ Not an API endpoint — the API holds no privilege on `readings` and would fail. `GET /operations/devices/{id}/recoverable` estimates; `python -m solarcms.cli backfill-device --device-id N` performs it under the ingest role.

**Planned work is not failure, and a renamed topic is not an outage.** `maintenance_windows` (0025) suppresses absence Alarms and is excluded from coverage, so routine servicing does not degrade the figure a guarantee is paid on; `device_id` NULL covers a whole Plant. `GET /operations/plants/{id}/topic-migrations` correlates a registered Device going silent with an unregistered topic appearing under the same Device code — the rename the client has now done twice in a week, which otherwise shows as an equipment outage on one screen and a new device on another, with nothing connecting them and somebody driving to site. It **proposes only**; the topic is the sole authority for origin, so a human confirms.

**A KPI now declares how much of the period it actually saw.** A gap does not make a figure look wrong, it makes it look *low* — an average over fewer samples is still an average, a total over a hole is simply smaller, and for availability a gap reads as nothing having happened. `GET /plants/{id}/kpis` returns a `coverage` block beside the values. It never corrects the figure; correcting it would be inventing data. ⚠ Expected samples are counted **per binding against each Tag's own throttle**, not per Device: counting one sample per Tag per message expected 367k readings a day against 26.6k stored and reported 7% on a Plant that was entirely healthy.

**Retention is a tier cascade**: raw 30d → `agg_1m` 1y → `agg_15m` 3y → `agg_1h`/`agg_1d` 10y. Each aggregate stores avg/min/max/last/count because a continuous aggregate cannot branch on `tags.rollup_method`; the read path picks the column. Reports query aggregates, never raw. The cascade is **hierarchical** — each tier reads the tier below — so lag compounds, which is why every tier runs with real-time aggregation on (`materialized_only = false`, migration 0023) and why anything reading a tier should pick it with `domain/tiering.select_tier` rather than naming one.

## Vocabulary is enforced

Canonical terms from MASTER §1 appear identically in table names, columns, classes, variables, API fields, UI labels, and log messages. The retired synonyms must not appear anywhere: **tenant/company/organisation** (→ Client), **site/facility/project** (→ Plant), **zone/section/array** (→ Block), **parameter/metric/point/signal** (→ Tag), **equipment/asset/unit** (→ Device), **alert/event/incident** (→ Alarm), **location** (retired entirely). Each was used for more than one concept. Use `clients`, `tags`, `alarms`, `device_tag_bindings`.

## Guardrails

These break something recorded as confirmed; BACKEND_SPEC §14 is the full list, MASTER §3.3 the invariants behind them.

1. Never a column per metric — metrics are rows in `tags`.
2. Never name a table, column, or code path after a specific Client, Plant, or Device (dashboards are configuration-driven; no per-Plant dashboards).
3. Never run ingestion inside the API process.
4. Never broadcast live data to all sockets — Client+Plant scoped rooms only.
5. Never infer a Client from payload contents. The MQTT topic `scms/v1/{client_code}/{plant_code}/{collector_code}/{device_code}` is the sole authority; an unknown topic is quarantined to `mqtt_raw` and alarmed, never attributed by inference.
6. Never let an assumed constant live outside `domain/assumptions.py`.
7. Never treat an empty `user_plant_access` as full access — zero assignments means zero Plants.
8. Never compute Financial Reports from MFM Readings — the ABT Meter is the sealed settlement instrument.
9. Never put I/O in `domain/`.
10. Never modify a `backend/`/`frontend/` prototype if one appears.
11. Never put a Block in the Single Line Diagram, and never nest Blocks.
12. Never register a Collector as a Device or draw one as a node in the diagram — it is an enclosure, drawn *around* its Devices. It owns exactly one edge (`plant_collectors.parent_device_id`); a Device inside it may never be wired to one outside it.
13. Never let anything but the topic decide which Collector a Device is in — a Device outside one cannot be put inside it, and one inside cannot be moved out or moved across.
14. Never draw a wire from a Collector to the Devices inside it — containment is what the box says, and seventeen wires would claim seventeen cables where the point is that there is one.
15. Never offer a topic that has stopped publishing as something to register — a Device registered against a dead topic never reports and is indistinguishable from broken equipment. Liveness is judged against the topic's own measured interval, never a fixed clock.
16. Never classify an absence as `equipment` — absence alone never proves which, and downtime we cannot evidence understates availability against a performance guarantee. Communication loss and equipment downtime are separate categories (tender §18).
17. Never raise one absence Alarm per Device when they share a Collector — it buries the cause and records one communication failure as many equipment failures.
18. Never report a KPI without its coverage — a period with a gap yields a figure that is low, plausible, and wrong in a way nothing else on the response reveals. Never "correct" a figure for a gap; that is inventing data.
19. Never order a diagram by type code. Alphabetical order has no electrical meaning, and as a tie-break it silently decides the whole row on an unwired Plant. Ties break by stage position; where nothing can be derived, say so instead of drawing a default.
20. Never read wiring from `devices.parent_device_id` alone. A Device inside a Collector has none — the room owns its edge — so a reader that ignores `plant_collectors.parent_device_id` will call a wired Plant unwired and push the operator towards the edit the server refuses.
21. Never auto-resolve a disagreement between the wiring and a Type default — the disagreement is a bug detector, and one of the two inputs is hand-typed and unverified. Report it, offer the assignments that satisfy the wiring, and let a human accept one.

22. Never plot two measures on one frame with two y-axes. The alignment between the two scales is arbitrary, so the chart asserts a correlation nobody measured — and irradiance against power is exactly the pair a reader invents a relationship from. Stack them on a shared time axis instead (`SmallMultiples`), where the eye can line up the times without the chart claiming a ratio.
23. Never draw a gap in a series as a value. A Plant that reported nothing was not producing zero, and a line drawn through the hole claims a number nobody measured — `connectNulls` stays off. A flagged reading is likewise never plotted as data, but the **count of flagged readings is shown**: an empty chart because every value was out of range and an empty chart because nothing arrived look identical and mean opposite things (a sensor reading −3 W/m² all night, versus a dead datalogger).
24. Never render a count with decimals. `digitsForUnit` settles it from the unit: there is no such thing as 0.4 of an Alarm, and "0.00" invites the reader to look for a precision that cannot exist.

25. Never let a summary open onto nothing. A card that expands to an empty panel, a stage that lists Devices with no way into one, a drawer whose content stops one step short of the screen that lets somebody act — each is a dead end that teaches people not to click. Every expander shows content, every Device row opens its inspector, and every drawer that has a fuller home names it.
26. Never show a blank where the reason is knowable. A Device with no bindings and a Device Type nobody has curated produce the same empty card and need opposite actions — the first decodes every message into nothing and is fixed in Tag Mapping, the second is fine. Say which.

27. Never average a Plant that was never due to report. `availability: 0.0` from a Plant with no Devices is not a measurement, and a fleet mean that counts it reports an estate that is not under-performing as though it were. Totals may count its zero; means may not.
28. Never hand a chart library a colour it cannot parse. Canvas is more forgiving than the library's own parser, so a wrong colour renders fine and then throws on the first animation. Route every chart colour through `theme/tokens`, which emits the legacy syntax and is tested against the parser.

29. Never render a Device's full detail inside a page's grid cell. It is a tall, variable-height thing next to fixed-height neighbours, so it stretches the page, shifts what is below it and becomes a ribbon on a wide screen. Detail opens in the drawer, at a fixed width, leaving the page exactly as it was.
30. Never rank a Plant that reported nothing. It lands at the bottom of a "worst performing" list and reads as the Plant most in trouble when nothing about it has been measured. Leave it out and say how many were left out — that count is itself the actionable item.

31. Never tie a chart library's lifecycle to a component's. Bind it to the container attaching and detaching — a callback ref — because the container is conditional on data that arrives later, and a mount effect fires before it exists. One disposal path only.
32. Never render a library-owned node and a React-owned node at the same position without distinct keys. React reuses the element, the library has already filled it, and the next swap throws `removeChild` and unmounts the page.
33. Never present a figure outside its physical range as a result. A ratio above 1 or below 0 means the numerator and denominator cover different spans. Show it unaltered, flag it, and point at the coverage — never clamp it into a shape that looks like a reading.

Two more worth holding in mind: out-of-range and unparseable values are **stored and flagged**, never discarded (`3.29151E-41` in a reactive-power Tag is diagnostic information); and MQTT is acknowledged only **after** commit, so a crash causes redelivery rather than loss — which is why the batch window is 2 seconds.

Two guardrails were added from the client's signal schedule: **never throttle a status Tag** (`min_interval_s = 0` on every Digital Input — a 60 s throttle discards a trip contact that opened and re-closed inside the window; enforced by a CHECK constraint in migration 0009), and **never write a threshold rule against a Device Type that publishes only Digital Inputs** — `TRANSFORMER` and `VCB` have no analogue value to compare, so they use the `is_true`/`is_false` operators instead.

## Things that surprised the build

Each of these was found by running the system, and each is a trap worth not re-discovering:

- **A payload key's meaning depends on the Device Type.** `VRY` is 11.037 from the client's MFM (an 11 kV feeder) and 799.9 from their Inverter (an 800 V LT bus). `SOURCE_KEY_ALIASES` is keyed by the key alone, so both resolved to `HV_VOLTAGE_RY` and one would have been stored as "799.9 kV" — with two of the three phases passing the range check while doing it. Use `alias_for(key, device_type_code)`, never the dict directly; `SOURCE_KEY_ALIASES_BY_DEVICE_TYPE` holds the overrides.
- **A subscription filter that matches nothing is invisible.** The client's broker moved to `SCMS/V1/...` while `MQTT_SUBSCRIBE_TOPICS` still said `KULAR_GREEN/#`. MQTT `#` is level-anchored, so it matched nothing, and because nothing was *delivered* nothing was quarantined either — `mqtt_raw` stayed empty and no alarm fired. 27 hours of silence looked exactly like a quiet plant. `python -m solarcms.cli commission-from-broker` (dry run by default) compares what is publishing against what is registered.
- **MQTT topic levels are case-sensitive, and must stay that way.** `SCMS/V1` is a second `topic_patterns` row, not a `.lower()` in the resolver: case-folding would make `KULAR_GREEN` and `kular_green` the same origin, and Guardrail 5 makes the topic the sole authority for origin.
- **Payloads come in two shapes.** The canonical envelope (`{device, timestamp, readings:[{tag,value}]}`) and the flat body the client's broker actually sends. `domain/decoding.normalise_payload` handles both. The envelope's `device` field is deliberately ignored — the topic is the sole authority for origin.
- **Throttling also erased the liveness signal.** `_accept` returned before recording anything when every Tag in a message was inside its throttle window, so a Device on 300 s-throttled Tags was invisible for 57 of every 60 s and the health sweep flapped it `online → offline` each minute. "Heard" and "stored" are now separate: ingest touches `seen:device:{id}` in Redis on every accepted message, and the sweep takes the later of that and `max(readings_v.time)`. Never derive liveness from `readings` alone.
- **A permissive RLS policy is not a GRANT.** Migration 0015 created `device_health_scheduler … WITH CHECK (true)` but never granted the scheduler INSERT/UPDATE, so every health sweep failed with "permission denied", logged it, and slept — `comm_status` stayed NULL fleet-wide and nothing else noticed. Fixed in 0017. A worker that catches-and-logs its main loop needs a test that asserts a row was written.
- **The integration suite runs against the dev database and leaves its fixtures behind** — `tests/conftest.py` says so (no Docker here). Every run adds ~30 Plants and ~35 Clients (`ESC-*`, `REP-*`, `iso-*`…), and an IDE test-runner that fires on save compounds it. Nothing tears them down.
- **Throttling also throttles alarm evaluation**, because the pipeline throttles before publishing to the alarm stream. Measured: detection latency is `min_interval_s + duration_s`, so a 60 s throttle plus a 60 s debounce opens an Alarm 120 s after onset. See BACKEND_SPEC §12.4.
- **A failed login cannot share a transaction with the 401 it records.** The raise rolls the audit row back, and tender §33 requires failed logins. `auth.py` commits that row in its own transaction first.
- **Authentication is circular**: `memberships` is needed to set `app.client_id`, but its policy filters on `app.client_id`. Resolved by setting `app.user_id` after the password verifies and letting a session read its own memberships (migration 0014). `SECURITY DEFINER` does *not* work here — `FORCE ROW LEVEL SECURITY` subjects the owner too.
- **asyncpg cannot infer a parameter's type used only in `IS NULL`**, and `:param::type` collides with SQLAlchemy's bind syntax. Use `CAST(:param AS type)`.
- **The same bind used twice can deduce two types and fail the whole statement.** `UPDATE plants SET status = :status … WHEN :status = 'active'` assigns to a `varchar(32)` and compares against a `text` literal, and asyncpg refuses with `inconsistent types deduced for parameter $1 — text versus character varying`. It surfaces as a 500 on a route that looks obviously correct. Same remedy as above: `CAST` **every** occurrence, not just the awkward-looking one.
- **`HTTPException(detail=...)` is rendered as a string.** A dict passed as `detail` reaches the browser as a Python repr — `{'message': …, 'issues': [...]}` — which then gets displayed to a user verbatim. Pass a sentence; if the caller needs structure, give it an endpoint to fetch.
- **`INET` comes back as `ipaddress.IPv4Address`**, which the JSON serialiser rejects; the audit query casts with `host()`.
- **RLS silently makes a migration's data fix a no-op.** `FORCE ROW LEVEL SECURITY` applies to the owner, so a migration that touches data in a protected table matches zero rows — no error, just nothing happening. Any such migration must `SELECT set_config('app.is_platform_admin','true',true)` first.
- **The scheduler runs with platform privileges, so the barrier views do not scope it.** Report generation must filter by `client_id` itself; it is the one place isolation is not inherited from the database, and it leaked another Client's meter into a Financial Report before the predicate was added.
- **`INSERT ... RETURNING` needs SELECT** on the returned columns, not just INSERT.
- **`coalesce(:param, column)` makes a PATCH unable to clear a field.** Every update route was written that way, which is right for a field the request did not mention and wrong for one it deliberately emptied — both arrive as `None`, so the two were indistinguishable and the old value survived. The symptom is the quiet kind: the field empties on screen, the request returns 200, and the value is back on the next read. Pydantic already knows the difference — `model_fields_set` holds exactly what the request *carried* — so assignments are now built from that (`api/patching.py`), giving PATCH its actual semantics: what you send is written, what you omit is left alone, and `null` means null. Audit rows take `exclude_unset`, never `exclude_none`, or a clearing records as nothing happening.
- **Commissioning-from-broker turned a room into a piece of switchgear.** The `{collector_code}` segment became an `MCR_SECTION` Device that seventeen Inverters pointed at as both `parent_device_id` and `reports_via_device_id`, so the operator's diagram showed the plant wired *through the control room* between the Inverters and the meter. Nothing errored; the shape was simply a lie. Fixed in migration 0022 — the Collector is a name, not a row.
- **A Super Admin could file a Plant under the wrong Client with no error anywhere.** `POST /plants` took `client_id` from the session only, and a Super Admin is a member of no Client — so the wizard made them *switch the session* into one first, and the Plant landed under whichever Client the session happened to hold. `client_id` is now a required field of the request for a platform admin and an ignored one for a Client Admin, which is the same isolation rule (I-9) with the guess removed.
- **Every continuous aggregate was materialized-only, and nobody asked for that.** `create_continuous_aggregate` has always taken `real_time: bool = True`, and only ever *wrote* the flag in the `False` branch — leaving the `True` case to TimescaleDB's default. That default flipped in 2.13 (`materialized_only` now defaults to `true`), so on 2.30 every tier was created the opposite of what the parameter said. Because the cascade is hierarchical (`agg_1m`←readings, `agg_15m`←`agg_1m`, `agg_1h`←`agg_15m`, `agg_1d`←`agg_1h`) each tier inherited the lag below it and added its own: **`agg_1h` was ~2.5 h behind**, and `GET /plants/{id}/kpis` read the hourly tier, so today's energy, PR and CUF were computed from data hours old on a screen whose whole purpose is *now*. Fixed in 0023. The general lesson: **a helper must never express intent by omitting a setting** — an omission is indistinguishable from a default that later changes underneath it.
- **`staleTime` is not a refresh interval, and reads exactly like one.** The Portfolio's KPI queries carried `staleTime: 30_000` and no `refetchInterval`, which means *no refresh at all* — `staleTime` only says when a value may be re-fetched, and with the global `refetchOnWindowFocus: false` nothing was going to ask. The figures were frozen at page load, silently and correctly-looking. Worse, the per-Plant KPI fan-out existed **twice** (`usePlantFleet` and `PortfolioDashboard`), so fixing one left the other frozen; it is now one shared `usePlantKpiFanout`. `tests/livecadence.test.ts` asserts the contract.
- **The broker probe read the envelope's wrapper as the Device's signals.** `tools/probe_broker.py` took `json.loads(payload).items()` directly, which is right for the flat body the test broker sends and silently wrong for the canonical envelope the contract specifies — it recorded `device`, `timestamp` and `readings` as that Device's three signals. Since `commission-from-broker` binds Tags from exactly those keys, registering an envelope publisher would have created **every Device with zero bindings**: equipment that exists, appears on every screen, and decodes nothing. It now calls `domain/decoding.normalise_payload`, the same function ingest uses — never a second copy of the rule. Measured on the canonical shape: 0 mapped / 3 junk keys before, 13 mapped / 0 unmapped after.
- **The Client's code must equal what the publisher puts in the topic, and a mismatch is invisible until a *new* Device appears.** The Client row said `kular-green` while every topic said `KULAR_GREEN`. Nothing broke, because the resolver's *first* path is an exact match on `devices.source_address`, which never compares the Client code at all — all 20 registered Devices resolved fine for weeks. Only the *pattern* path compares it (`c.code = :client_code`), and that is the path a newly-appeared Device takes, so the first Device the client added would have been quarantined as "no Device registered for this topic" while its topic was perfectly valid. Corrected to `KULAR_GREEN` on 19 Sep 2026. ⚠ Not a case-folding problem — `kular-green` and `KULAR_GREEN` differ by hyphen-vs-underscore too, and folding origins is forbidden by Guardrail 5 regardless.
- **An uncontrolled input that commits on blur will write stale values by itself.** The hierarchy editor's collector box used `defaultValue` with a `key` carrying the stored value, and committed `onBlur`. When that value changed underneath it — a refresh, or an edit made elsewhere — React unmounted the old node, the browser fired `blur` on it *as it was removed* carrying the pre-change value, and the handler wrote it straight back. It silently re-applied `collector_code = 'MCR'` to two Devices that had just been moved out of the MCR, from a page nobody was touching, and the audit log recorded it as a deliberate edit. A blur now commits only if a keystroke preceded it (`editedCollectors` ref): a field nobody typed in cannot write.
- **The live socket is a trigger for the KPI tiles, never a source.** A dashboard slot is resolved on the server against what the Plant is actually bound to, and provenance travels with the value — 6.32 MW measured and 6.32 MW summed are different claims, and only the server knows which it just made. So `useLiveRefresh` invalidates `plants/{id}/dashboard` and `plants/{id}/kpis` when a frame for that Plant arrives (coalesced 1s, because twenty Devices reporting in one round would otherwise queue twenty refetches), and the figure still comes from the server. The polling timer becomes a backstop at 30s while the socket is open and tightens back to 5s/10s when it closes, so this is a net *reduction* in requests rather than an addition. Measured: silent 6s → 0 requests; one frame → both tiles refetch 1.1s later; 40s idle went from 12 requests to 2. ⚠ It cannot make a tile fresher than the equipment — it removes only the delay *we* were adding.
- **A table or column missing from the ORM is one `--autogenerate` believes you deleted.** The routers use explicit SQL, so a model is not needed at runtime and three of them were simply never written — `plant_collectors` (0024), `plant_device_counts` (0019) and the five commercial columns 0019 added to `clients`. Nothing broke, because nothing reads them through the ORM. But `alembic revision --autogenerate` compares the database against `Base.metadata`, so it proposed **`DROP TABLE plant_collectors`** (every Plant's collector wiring) and **dropping every Client's GSTIN, account number and contract dates**. The generated migration would have looked entirely routine. Models added 19 Sep 2026; `alembic check` now emits no destructive operation. ⚠ Run `alembic check` before writing a migration by hand, and never trust an autogenerated one that contains a DROP you did not ask for. The residual noise it still reports — `modify_comment`, `modify_default` on Identity columns, `modify_type` — is cosmetic and safe to ignore.
- **A permissive RLS policy is not a GRANT — and it happened a second time.** Migration 0015 gave the scheduler SELECT and UPDATE on `alarms`, an `alarms_scheduler` policy `WITH CHECK (true)`, and **no INSERT**. Every absence Alarm the health sweep tried to raise would have failed exactly the way `device_health` did in 0015/0017: permission denied, logged, slept, nothing written, nobody told. Granted in 0025. The lesson holds — when a worker catches-and-logs its main loop, a test must assert a row was *written*, not that the code ran.
- **`operator = 'special'` rules were rows with no evaluator.** `COMM_LOST`, `COLLECTOR_OFFLINE`, `FROZEN_SENSOR`, `INV_UNDERPERFORMANCE` and `STRING_CURRENT_DEVIATION` were seeded and enabled, and `alarm_logic.py` says plainly that it does not handle `special`. The health sweep computed every fact needed for the first two — it wrote `comm_status` and logged a correlation — and raised nothing. Measured: **zero Alarms had ever been written**, while 11 of 21 Devices sat "degraded" and two published unregistered for an hour. Absence alarming is built (0025); `FROZEN_SENSOR`, `INV_UNDERPERFORMANCE` and `STRING_CURRENT_DEVIATION` remain unevaluated.
- **A payload key can be a *string* boolean, and it decodes to nothing.** The client's VCB publishes `"ON": "TRUE"`, not `true`. `coerce_value` handled JSON booleans and `float()` — so every Digital Input coerced to None and stored flagged unparseable. All twelve VCB signals are contacts, so the Device would have looked registered, healthy and online while carrying no readable value at all; the PPC was silently losing five of its ten signals in production. Measured before the fix: PPC 105 good / 105 unparseable. After: 10/10, and VCB 12/12.
- **`expected_interval_s` left at a stale value flags a healthy fleet as degraded.** The whole Plant moved to an 86s cycle while every Device was still registered at 31s, and the sweep calls a Device degraded at twice its interval — so 11 of 21 read degraded permanently. Registered from measurement, never from the default.
- **Charts vanished because the hook initialised once and disposed twice.** Three defects in `useEcharts`, all of which read from outside as "the graph keeps disappearing" while the panel kept its layout and its title. (1) `useRef` plus a mount effect found `ref.current === null` whenever the container was behind a loading or empty branch — which it is on every first paint — and with an empty dependency array it never ran again, so the chart was blank for the session. (2) React 18's StrictMode re-runs *effects* but **not ref callbacks**, so an `useEffect(() => () => chart.dispose(), [])` destroyed the instance the ref callback had created and nothing rebuilt it; only charts present at the first paint (the KPI gauges in a drawer) were hit, which is why it hid for so long. (3) The empty, table and chart branches all rendered a bare `div` at the same position, so React **reused the node** ECharts had filled and the next swap threw `NotFoundError: Failed to execute 'removeChild'`, unmounting the whole dashboard. The hook is now a **callback ref** — attach initialises and paints the latest option, detach disposes, and disposal lives nowhere else — and each branch carries its own `key`. ⚠ Do not add an unmount effect back; `tests/chartmount.test.tsx` fails if you do.
- **A gauge cannot draw 389%, so it drew 100%.** `/kpis?period=month` returned a Performance Ratio of **3.89** — a month of Inverter energy over irradiance the weather station reported for 15% of it. The gauge clamped its arc to the 0..100 range and printed "389.2%" beside it, so the ring said *perfect* and the number said *impossible*, and the ring is what gets read at a glance. `ratioIsImplausible` flags a ratio outside what the quantity can physically be; the figure is shown **unaltered** — correcting it would invent data and hiding it would conceal the gap that produced it — but presented as a fault rather than a result. ⚠ The ceiling is deliberately loose (1.2): a PR slightly above 1 is real in cold, bright conditions, and flagging good data is its own kind of lie.
- **Rendering detail in a grid cell made it a ribbon.** The Single Line Diagram put the full Device inspector in a 20rem column beside a 460px diagram, so selecting a Device with eighteen Tags and a chart stretched the page, shifted everything below and left a long narrow strip to scroll — on the one screen whose whole job is a diagram you are pointing at. Clicking a stage did the same, expanding *between* the schematic and the power path. Both now open the shared drawer: the page height does not change at all, and the panel is a fixed column at every width instead of whatever a grid cell happened to leave over. Escape steps back (Device → stage list → closed) rather than dismissing everything at once.
- **An icon that is merely thematic teaches the wrong thing.** A location pin beside "DC capacity" says *where* about a figure that means *how big*; a bolt beside an energy total says *rate* about a figure that is an accumulation. Tile icons are now chosen per quantity — the array for capacity, an accumulating bar series for energy, a gauge for a bounded ratio, a clock with a segment missing for availability, a leaf for CO₂ — and they carry the brand accent only, because status owns green, amber and red and a tinted chip beside a figure reads as a judgement about it.
- **Every colour the app gave ECharts was unparseable by ECharts, and charts vanished on hover.** The theme tokens are stored as space-separated channels because Tailwind's `rgb(var(--x) / <alpha-value>)` needs them that way, and `token()` emitted them in the same shape — `rgb(42 120 214)`, CSS Color Level 4. The browser parses that, so a canvas filled with it and **every chart rendered correctly**. zrender's own parser predates Level 4 and returns `undefined`, so nothing broke until something *interpolated* a colour — which is exactly what hovering a series does. The result was `TypeError: Cannot read properties of undefined (reading 'length')` thrown from inside `interpolate1DArray`, and the chart disappearing. A rendering test could never have caught it; `tests/tokens.test.ts` now runs every emitted colour through zrender's parser. **Legacy `rgb(r,g,b)` / `rgba(r,g,b,a)` only.**
- **ECharts hands a tooltip epoch milliseconds, and the date formatters only took `Date | string`.** On a `type: "time"` axis `axisValue` is a number, so any tooltip that formatted the axis value rather than the datum threw `date.getTime is not a function` — *inside a render*, which unmounts the chart. TypeScript could not catch it: the value arrives from ECharts typed `unknown` and is narrowed by hand. `format/datetime` now takes a `Timestamp = Date | string | number`.
- **A single reading on a line chart draws nothing at all.** A line needs two vertices, and with `showSymbol: false` one point produces a blank plot with axes — which reads as "no data" when the truth is "one reading". Silent, plausible, and the worst of the chart edge cases. Below three points the symbols come back on. `/dev/charts` is the contact sheet of every shape that breaks a chart; `/dev/art` is its equivalent for the equipment drawings.
- **ECharts does not measure axis labels against the grid.** A lifetime counter ticks at 1,500,000 — nine characters — and against a fixed 52px gutter the leading digit was simply cut off: the axis read `,500,000`. Silently losing the most significant digit of a scale is about the worst thing an axis can do. Ticks now compact above 10,000 (a tile has room for `999,999`, an axis tick does not) and the gutter is sized from the widest label that will actually be drawn. ⚠ `formatCompact` uppercases for the reason `formatHeadline` already documented — `1.5m kWh` reads as *milli* to precisely this audience, and on an axis the suffix sits right beside the unit.
- **`sample_count` arrives as a JSON string, and it blanked every aggregate chart.** It is a `count(*)`, so Postgres types it `BIGINT`, and the driver path serialises BIGINT as a string to dodge the 2^53 precision cliff. The zod schema declared `z.number()`, and because the whole envelope is parsed at once, one `"10"` failed the entire response with "Unexpected response shape from GET /readings". The raw tier carries no `sample_count` at all, which is why it only ever broke on ranges long enough to be served by an aggregate — so the short windows everyone tested worked and the long ones did not.
- **The chart palette was not colourblind-safe, and the two worst slots were adjacent.** Series 1 (blue `#2f7fd1`) and series 2 (violet `#7a6cd6`) sat **ΔE 0.8 apart under deuteranopia** and 9.1 under normal vision — on a chart of seventeen Inverters, two lines were the same colour to everybody and three were the same colour to one reader in twelve. `#64748b` also fell under the chroma floor and read as grey. Replaced with a validated eight-slot set; **the slot order is the safety mechanism, not a preference**, so re-ordering or substituting "a similar hue" breaks it. Verified against this app's own surfaces with the palette validator — every check passes in both themes.
- **The live socket carries only *new* frames, so cards opened empty.** A Device here publishes every 86 seconds, so a freshly loaded dashboard showed a row of Inverter cards reading "—" for up to a minute and a half on equipment that was running perfectly. Dashes mean "we have no value", and having none because nobody has spoken *since you arrived* is not a fact about the plant. `api/useLatestValues.ts` seeds from stored readings and the socket overwrites per Device — merged **per Tag**, because a frame carries only the Tags that were not throttled in that message and taking it wholesale blanked the figures that were not in it. ⚠ Stored readings are not a liveness signal; `comm_status` remains the only thing that says whether a Device is reporting.
- **A diagram that fits is not the same as a diagram you can read.** `DiagramCanvas` fitted the whole tree on first paint, which on a Plant with seventeen Inverters side by side chose **23%** — every box a smudge, every label gone. The automatic fit now stops at a legibility floor and pans instead; pressing *Fit* still frames the whole thing, because that is a deliberate request for the shape rather than the detail.
- **Appending hex alpha to an `rgb()` string throws inside ECharts.** `${color}44` is the reflex from hex, and against `rgb(57 135 229)` it yields `rgb(57 135 229)44`, which the canvas rejects at `addColorStop` — the error names neither the chart nor the caller, and the whole chart fails to paint. `theme/tokens.withAlpha` is the only way to make a translucent series fill.
- **A curated list became a precondition instead of an improvement.** The Device carousel was built from `device_table_columns`, which is right — those rows are configuration, so a Client changes what their cards show without a release. But types with no rows were *dropped*, and on this Plant that silently removed the breaker, the plant controller and the KPI panel from the Plant screen entirely: six registered Devices with no route to them from the screen whose job is to show the Plant. `api/useTypeColumns.ts` falls back to one Device's own bindings. ⚠ The fallback reads a **Device**, never its Model — a Model's signal schedule is a starting point for bindings, not their authority, so it can be true of none of the units.
- **`h-4.5` compiles, lints, and emits nothing.** Tailwind's default spacing has fractional steps only at 0.5, 1.5, 2.5 and 3.5. `h-4.5` on an icon chip meant to be a fixed square produced no height at all and the element took whatever its content gave it — the same silent failure as an undefined colour, in a different scale. `tests/tokens.test.ts` now fails on any fractional step Tailwind does not define.
- **A daily bucket rendered with a time claims a reading that was never taken.** `17-09-2026 05:30:00` on the energy-per-day chart is the whole of the 17th; the 05:30 is only UTC midnight expressed in Asia/Kolkata. `formatBucket` takes the tier and drops the time at `agg_1d`, the same reasoning `formatAxisLabel` already applied to axes.
- **A Digital Input through the numeric path reads `0.00 bool`.** Three things wrong at once: it invites arithmetic on a state, it implies a precision a contact cannot have, and `bool` is a type name leaking onto an operator's screen as a unit. Roughly a third of Tags are Digital Inputs and the whole of VCB and TRANSFORMER is, so it was most of what those cards showed.
- **ECharts anchors a markPoint label and never reflows it.** A peak in the last minutes of the window — which on a rising day is where a generation curve peaks — pushed "peak 235 kW" off the right of the plot and rendered it as "peak 235 k". The label now flips inboard near either edge.
- **Three runtime roles, not two**: `solarcms_api`, `solarcms_ingest`, `solarcms_scheduler`. The scheduler reads alarms, escalations and users — none of which ingestion should see.

## Blocked work

MASTER §8.1 lists fourteen open items awaiting a client answer. Do not build numeric display, reports, or thresholds as if settled: **OPEN-15** (unit and scale per Tag), **OPEN-16** (the client's PR/CUF/Availability formulas), **OPEN-14** (counters vs instantaneous, rollover maximum, ABT-vs-MFM precedence) gate anything that shows or computes a number. Observation of the data stream reveals shape, never meaning (MASTER §5.4) — resist treating these as discovery tasks.
